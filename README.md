# Cloud Infra Day 7

인프라 엔지니어의 기본 업무를 작은 장애 대응 과제로 경험하는 **7일 입문 실습**입니다. 1일은 달력상의 의무가 아니라 하나의 학습 단위입니다. 하루 30~40분 개념·관찰, 40~50분 실습과 기록을 권장하며 시간이 부족하면 나누어 진행합니다.

> **진행 상태: 계획**. 이 저장소의 과제는 아직 수행한 결과가 아닙니다. 직접 실행한 증거를 기록한 뒤에만 완료 표시합니다.

## 준비물과 규칙

- Ubuntu 테스트 VM(예: Multipass), 터미널, 인터넷.
- AWS 실습은 Day 5에 선택합니다. AWS 계정이 없다면 아키텍처와 공식 가이드로 설계만 하고, 미실행이라고 기록합니다.
- AWS는 요금이 발생할 수 있습니다. 실습 전 [요금](https://aws.amazon.com/ec2/pricing/)과 [예산 알림](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)을 확인합니다. 예산 알림은 비용 발생을 자동 차단하지 않습니다. 인스턴스뿐 아니라 퍼블릭 IPv4, 디스크 등 남은 리소스를 확인해 정리합니다.
- SSH 개인키, 비밀번호, 공개 IP, 계정 번호, 민감 로그와 토큰은 GitHub에 올리지 않습니다. 테스트 VM에서만 장애를 재현합니다.
- AI에는 개념 설명과 힌트를 먼저 요청합니다. 명령을 직접 이해하고 실행하며, 결과를 만들어 내지 않습니다.

## 실습 순서

|---|---|---|---|

| 2 | 네트워크 | 로컬 IP, DNS, 연결 포트와 HTTP 요청 경로를 살펴본다. | 요청 흐름과 실패 지점 구분 |
| 3 | 웹 서버 운영 | 테스트 VM에 Nginx를 설치하고 응답과 중단·복구를 확인한다. | 상태·포트·응답과 복구 기록 |
| 4 | 컨테이너 운영 | Docker로 웹 컨테이너를 실행하고 상태와 로그를 확인한다. | 호스트 포트와 컨테이너 응답 확인 |
| 5 | 클라우드 운영 | EC2·VPC·서브넷·보안 그룹의 관계를 설계한다. AWS 실습은 선택. | 구성도와 요청 경로, 비용·정리 계획 |
| 6 | 운영·인수인계 | 웹 서비스의 점검 및 복구 절차를 작성하고 검증한다. | 따라 할 수 있는 운영 절차와 결과 |
| 7 | 회고 및 진로 | 직무별 경험을 돌아보고 장애를 설명한다. | 실습 결과·직무 선호·다음 학습 정리 |

## Day 1 — Linux 상태 확인

**티켓:** “서버가 느리다는 제보가 들어왔다. 먼저 현재 상태를 확인해 주세요.”

- 학습: 프로세스, 메모리의 available, 디스크 사용률, systemd 상태. [Ubuntu 서버 가이드](https://documentation.ubuntu.com/server/)
- 실습: VM에서 `uptime`, `free -h`, `df -h /`, `systemctl --failed`의 의미를 이해하고 실행한다. 결과 해석에 집중한다.
- 검증: 각 결과가 무엇을 뜻하는지와 현재 주의할 항목을 기록한다. 한 번의 관찰만으로 장애가 없다고 단정하지 않는다.
- 질문: 메모리의 free와 available은 왜 다른가?

## Day 2 — 네트워크 경로

**티켓:** “웹페이지가 열리지 않는다. 어디서부터 확인해야 할까?”

- 학습: IP, DNS, TCP 포트, HTTP 응답. [MDN HTTP 개요](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)
- 실습: VM에서 `ip addr`, `getent hosts example.com`, `ss -lnt`, `curl -I https://example.com`을 확인하고 결과를 해석한다.
- 검증: DNS 조회와 HTTP 요청 중 실패한 단계가 있으면 구분해 기록한다. IP와 포트는 공유 전 가린다.
- 질문: 이름 해석이 성공해도 웹 요청은 왜 실패할 수 있을까?

## Day 3 — Nginx 서버와 장애 복구

**티켓:** “테스트 서버에 상태 페이지를 띄워 주세요.”

- 학습: 패키지, systemd 서비스, 포트 80, HTTP 응답. [Ubuntu Nginx 가이드](https://documentation.ubuntu.com/server/how-to/web-services/install-nginx/)
- 실습: 테스트 VM에 Nginx를 설치하고 `systemctl status nginx`, `ss -lnt`, `curl -I http://127.0.0.1`로 상태와 응답을 확인한다. 설치 과정은 직접 조사한다.
- 검증: 서비스 상태, 수신 포트, HTTP 상태 코드를 기록한다. 테스트 VM에서 서비스를 중지하고 증상과 상태를 확인한 뒤 복구하고 재확인한다. 시간이 부족하면 중단·복구를 별도 블록으로 나눈다.
- 질문: 서비스가 실행 중이어도 클라이언트가 접속하지 못하는 이유는?

## Day 4 — Docker 컨테이너 운영

**티켓:** “같은 웹 서비스를 격리된 환경에서 실행하고 상태를 확인해 주세요.”

- 학습: 이미지와 컨테이너, 포트 연결, 로그. [Docker 시작하기](https://docs.docker.com/get-started/)
- 실습: Docker가 준비된 테스트 환경에서 공식 Nginx 이미지를 실행하고 호스트의 임의 포트와 연결한다. Docker가 없다면 설치와 첫 실행을 별도 블록으로 나눈다.
- 검증: 실행 중인 컨테이너, 로그, HTTP 응답을 확인하고 종료·삭제한다. 실행하지 못한 경우 계획으로 기록한다.
- 질문: 호스트 프로세스와 컨테이너를 구분할 때 무엇을 확인할 수 있는가?

## Day 5 — AWS 구성 이해

**티켓:** “외부에서 접근할 테스트 웹 서버를 AWS에 배치한다면?”

- 학습: EC2, VPC, 서브넷, 라우팅, 보안 그룹. [EC2 시작하기](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/EC2_GetStarted.html)
- 실습: 브라우저 → 인터넷 → VPC → EC2 → Nginx 흐름을 그린다. 필요한 인바운드 접근과 관리 접근을 구분한다. 관리 포트를 전체 인터넷에 무제한으로 열지 않는다.
- 선택: 계정·요금·보안을 준비한 경우에만 EC2를 만들고 접속을 확인한다. 실습 후 리소스를 정리한다.
- 검증: 직접 실행한 것과 설계만 한 것을 분리한다. 리소스 및 비용 확인 방법을 기록한다.
- 질문: 서버의 서비스가 정상이어도 보안 그룹 때문에 접속이 막힐 수 있는 이유는?

## Day 6 — 운영 점검과 인수인계

**티켓:** “다음 담당자도 서버 상태를 같은 순서로 확인할 수 있게 해 주세요.”

- 학습: 운영 절차서(runbook)의 목적과 종료 상태.
- 실습: Day 1~5에서 직접 쓴 확인 순서를 서비스 상태 → 포트 → HTTP 응답 → 로그 순으로 정리한다. 여유가 있다면 한 항목을 셸 스크립트로 직접 작성한다.
- 검증: 절차를 따라 정상 상태를 확인한다. 스크립트를 작성한 경우 정상과 서비스 중단 상태에서 결과를 비교하고 복구한다.
- 질문: 명령 하나가 실패했을 때 담당자는 다음에 무엇을 확인해야 하는가?

## Day 7 — 회고와 직무 탐색

- Day 3 장애를 1분 안에 증상, 확인한 근거, 원인, 조치, 복구 검증 순서로 설명한다.
- Linux, 네트워크, 웹 서버, Docker, AWS 중 흥미와 어려움을 각각 기록한다.
- 직접 실행한 일과 설계만 한 일을 구분하고, 다음에 깊이 배우고 싶은 분야를 하나 고른다.
- 검증: 기록을 보지 않고 요청 경로와 장애 확인 순서를 설명해 본다.
